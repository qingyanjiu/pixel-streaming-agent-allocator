# Pixel Streaming 服务启动说明

本文只说明如何启动和停止按需分配的 Pixel Streaming 服务。客户端接入细节见 [客户端连接像素流说明.md](客户端连接像素流说明.md)。

从空白机器安装 Allocator、Worker 和 Gateway 的完整步骤见 [部署文档.md](部署文档.md)。

除特别说明外，本文路径和命令都相对于项目根目录。

组件关系、Slot 与 UE 进程、调度流程和扩展边界见 [架构说明.md](架构说明.md)。

Worker Token、Client API Key 和常见认证错误见 [认证与密钥说明.md](认证与密钥说明.md)。

Gateway、Ticket 校验、HTTPS 和直接端口保护见 [Gateway网关说明.md](Gateway网关说明.md)。

前端联调接口和示例见 [客户端连接像素流说明.md](客户端连接像素流说明.md)。

Allocator 和 Worker 控制台日志的查看方法见 [调试与日志说明.md](调试与日志说明.md)。

Allocator 启动后可通过 [流资源驾驶舱](驾驶舱说明.md) 查看 Worker、Slot、就绪数和占用情况：

```text
http://Allocator-IP:9200/dashboard/
```

## 1. 目录说明

服务按部署职责位于独立目录：

```text
Allocator
Worker
Gateway
```

推荐保持统一部署根目录：

```text
项目根目录\
├── Allocator\
├── Worker\
├── Gateway\
├── Docs\
├── WebServers\
└── ...
```

Windows 游戏构建可以独立配置：

```json
{
  "windowsDirectory": "<Windows构建目录>",
  "webServersDirectory": "../WebServers",
  "nodeExecutable": "SignallingWebServer/platform_scripts/cmd/node/node.exe",
  "signallingDirectory": "SignallingWebServer",
  "gameExecutable": "UE_ANDA.exe",
  "gameWorkingDirectory": ".",
  "logsDirectory": "logs"
}
```

相对路径规则：

| 字段 | 解析位置 |
|---|---|
| `gameExecutable` | 相对于 `windowsDirectory` |
| `gameWorkingDirectory` | 相对于 `windowsDirectory` |
| `signallingDirectory` | 相对于 `webServersDirectory` |
| `nodeExecutable` | 相对于 `webServersDirectory` |
| `logsDirectory` | 相对于 Worker 根目录 |
| `peerOptionsFile` | 相对于 Worker 配置文件目录 |

也可以全部使用绝对路径。

当前实际 Allocator 和 Worker 地址配置已提交到 Git。仅在恢复配置或需要新增 Worker 时从示例复制：

```powershell
Copy-Item `
  "Allocator\allocator.example.json" `
  "Allocator\allocator.json"

Copy-Item `
  "Allocator\config\workers.example.json" `
  "Allocator\config\workers.json"
```

Gateway Token 文件以占位值提交，部署时必须替换；日志、TLS 私钥和 `.env` 不会提交到 Git。

## 2. 启动前必须检查

### 2.1 检查所有 Worker 地址

每台 Worker 使用自己的配置，例如：

命名统一为 Worker `worker01`、Slot `slot01`；不同 Worker 可以使用相同的 Slot ID。完整规则见
[Worker 与 Slot 命名规范](命名规范.md)。

```text
Worker\worker01.json
Worker\worker02.json
...
Worker\worker20.json
```

可以从配置模板复制：

```powershell
Copy-Item `
  "Worker\worker-template.json" `
  "Worker\worker01.json"
```

每份配置修改唯一的 `agentId`、Token 和槽位端口。`publicUrl` 保留为 Allocator 未启用 Gateway 时的兼容直连地址：

```json
{
  "id": "slot01",
  "publicUrl": "http://Worker01IP:801/"
}
```

Worker 固定地址统一修改：

```text
Allocator\config\workers.json
```

文件中的每个 Worker 同时配置管理地址和 Gateway 地址：

```json
{
  "workers": [
    {
      "id": "worker01",
      "baseUrl": "http://Worker01IP:9101",
      "gatewayUrl": "http://Worker01IP:9300"
    },
    {
      "id": "worker02",
      "baseUrl": "http://Worker02IP:9101",
      "gatewayUrl": "http://Worker02IP:9300"
    }
  ]
}
```

依次增加全部 20 个 Worker。必须保证：

- `baseUrl`、`gatewayUrl` 和对应 Worker 配置都指向同一台机器。
- 每台机器的 `agentId` 和 `workers.json` 中的 Worker `id` 唯一且一致。
- `baseUrl` 使用 `9101`。
- `gatewayUrl` 使用 `9300`，HTTPS 部署时使用 `https://`。

### 2.2 检查 Token 和 API Key

每个 Worker 的 `authToken` 必须与其在 `Allocator/config/workers.json` 中的 `token` 一致。

如果配置中仍有以下占位值，应全部替换：

```text
replace-with-a-long-random-worker-token
replace-with-a-long-random-client-api-key
```

Allocator 的 `apiKey` 是客户端申请实例时使用的密钥。

Gateway 和 Allocator 还必须共享同一个 Gateway Token。首次部署运行：

```bat
scripts\initialize-gateway-token.bat
```

生成的文件：

```text
secrets\gateway-token.txt
```

Allocator 通过 `allocator.json` 的 `gatewayTokenFile` 读取；每台 Gateway 通过 `gateway.json` 的 `allocatorTokenFile` 读取。多机部署时必须复制同一份实际 Token 文件。完整步骤见 [部署文档](部署文档.md)。

### 2.3 检查文件路径

确认 Worker 配置指向的文件存在：

```text
<游戏构建根目录>\Windows\UE_ANDA.exe
WebServers\SignallingWebServer\dist\index.js
WebServers\SignallingWebServer\www\player.html
```

如果各 Worker 的目录不同，分别修改每台机器的配置，不需要保持相同路径。

### 2.4 不要同时启动旧脚本

不要同时运行：

```text
<UE项目根目录>\_startexe-.bat
```

旧脚本会直接占用 `801/802`、`8001/8002` 和 `9001/9002`，与 Worker Agent 冲突。

## 3. 启动顺序

### 3.1 启动全部 Worker Agent 和 Gateway

每台机器使用自己的配置调用通用启动器，例如：

```bat
Worker\start-worker.bat worker01.json
```

如果配置文件不在 `Worker` 目录中，可以传入完整路径：

```bat
Worker\start-worker.bat Worker\worker01.json
```

每台机器分别使用 `worker01.json` 到 `worker20.json`。启动器会：

- 在新的命令窗口启动该机器的 Gateway。
- 把当前 Worker 配置传给 Gateway，确保 `worker02` 不会误读 `worker01.json`。
- 在当前窗口启动 Worker Agent `9101`。
- 不会立即启动 UE，收到 Allocator 分配后才启动对应 Slot。

指定其他 Gateway 配置：

```bat
Worker\start-worker.bat worker02.json ..\Gateway\gateway-worker02.json
```

只启动 Worker，不启动 Gateway：

```bat
Worker\start-worker.bat worker01.json --no-gateway
```

### 3.2 启动 Allocator

在中央机器运行：

```bat
Allocator\start-allocator.bat
```

保持命令窗口运行。Allocator 默认监听 `9200`。

### 3.3 单独启动 Gateway

通常不需要这一步，因为 `start-worker.bat` 已自动启动 Gateway。

在对应 Worker 机器运行：

```bat
Gateway\start-gateway.bat
```

`Gateway/gateway.json` 默认读取 `Worker/worker01.json`。单独在 `worker02` 机器启动时，可以传入 Worker 配置：

```bat
Gateway\start-gateway.bat gateway.json ..\Worker\worker02.json
```

Gateway 默认监听 `9300`。启动顺序也可先启动 Allocator，再启动 Worker 和 Gateway；客户端申请前三者都必须可用。

## 4. 启动后的健康检查

### 4.1 检查所有 Worker Agent

```text
http://Worker01IP:9101/health
http://Worker02IP:9101/health
...
http://Worker20IP:9101/health
```

正常响应示例：

```json
{
  "ok": true,
  "agentId": "worker01",
  "slotCount": 2
}
```

### 4.2 检查 Allocator

```text
http://Allocator机器IP:9200/health
```

正常时应显示 20 个 Worker 在线：

```json
{
  "ok": true,
  "onlineWorkers": 20,
  "workerCount": 20
}
```

### 4.3 检查 Gateway

```text
http://Worker01IP:9300/health
```

正常响应包含：

```json
{
  "ok": true,
  "agentId": "worker01",
  "slots": ["slot01", "slot02"]
}
```

`9300/` 根路径不提供播放器页面；只有带有效 Ticket 的 `/play/...` 地址可以访问。

### 4.4 检查所有槽位

```powershell
Invoke-RestMethod `
  -Uri "http://Allocator机器IP:9200/api/slots" `
  -Headers @{ "X-API-Key" = "你的 allocator apiKey" }
```

如果每个 Worker 配置两个槽位，应看到类似：

```text
slot01
slot02
slot01
slot02
...
slot01
slot02
```

初始状态通常为 `stopped`。此时还没有启动 UE 进程。

## 5. 第一次分配实例

申请一个实例：

```powershell
$headers = @{
    "X-API-Key" = "你的 allocator apiKey"
    "Idempotency-Key" = [guid]::NewGuid().ToString()
}

$session = Invoke-RestMethod `
    -Method Post `
    -Uri "http://Allocator机器IP:9200/api/sessions" `
    -Headers $headers `
    -ContentType "application/json" `
    -Body '{"ttlSeconds":3600}'

$session
```

第一次分配一般会返回：

```text
status = starting
message = 正在启动 Pixel Streaming 服务，请稍候...
sessionToken = ...
```

创建响应中的 `sessionId`、`sessionToken` 和 `url` 需要由客户端保存。

轮询会话：

```powershell
Invoke-RestMethod `
  -Uri "http://Allocator机器IP:9200$($session.pollUrl)" `
  -Headers @{
      "X-API-Key" = "你的 allocator apiKey"
      "X-Session-Token" = $session.sessionToken
  }
```

状态变为 `ready` 后，打开响应中的 `url`。

## 6. 检查启动日志

按实际分配的槽位查看：

```text
Worker\logs\worker01\slot01\wilbur.log
Worker\logs\worker01\slot01\ue.log
Worker\logs\worker01\slot02\wilbur.log
Worker\logs\worker01\slot02\ue.log
```

其他 Worker 使用自己的 `agentId` 和槽位 ID：

```text
Worker\logs\worker02\slot01\
Worker\logs\worker02\slot02\
```

Wilbur 正常启动后，日志中应看到：

```text
Streamer connected: DefaultStreamer
```

## 7. 释放测试会话

测试完成后主动释放：

```powershell
Invoke-RestMethod `
  -Method Delete `
  -Uri "http://Allocator机器IP:9200/api/sessions/$($session.sessionId)" `
  -Headers @{
      "X-API-Key" = "你的 allocator apiKey"
      "X-Session-Token" = $session.sessionToken
  }
```

当前配置会在以下情况自动回收：

- 返回地址后 `connectTimeoutMs=600000` 内没有玩家连接。
- 玩家断开后进入 `disconnected`，`idleReleaseMs=600000`。
- 断线后的 10 分钟内，同一 Session 可以重连。
- 新用户不会获得正在等待重连的 Slot。
- 10 分钟内没有重连时再释放 Slot。
- 如果 Worker 返回 `stopped` 或 `failed`，Allocator 立即释放租约，不等待 10 分钟。
- 会话超过 `ttlSeconds`。
- `stopOnRelease=true` 时，释放后会停止对应 UE 和 Wilbur。

前端可在等待期间直接展示响应中的 `message`。`disconnected` 状态下，`reconnectDeadline` 给出最晚重连时间。

手动执行 `stop-slot.bat` 后：

1. Worker 停止 UE/Wilbur。
2. Allocator 在约 2 秒的轮询周期内识别终止状态。
3. 原 Session 立即变为 `released`。
4. 新客户端可以重新申请并启动该 Slot。

## 8. 停止服务

手动结束 UE 进程的影响和 Slot 恢复方式见
[UE 进程与 Slot 停止说明](UE进程与Slot停止说明.md)。

停止全部 Gateway、Worker Agent、它们管理的所有 UE/Wilbur，以及本地 Allocator：

```bat
stop-all.bat
```

默认需要输入 `YES` 确认。自动化场景使用：

```bat
stop-all.bat --force
```

只预览操作：

```bat
stop-all.bat --what-if
```

`stop-all.bat` 会先读取 `workers.json`，关闭所有 Gateway，再通知在线 Worker 停止全部 Slot 并退出，最后关闭 Allocator。

如果本机 Allocator 版本较旧、没有 `/shutdown` 接口，脚本会按 `9200` 监听端口找到本地 Node 进程作为回退并结束它。

如果某个 Worker 已离线，脚本无法远程清理该机器上的残留 UE/Wilbur；需要在对应机器本地处理。

关闭 Worker 上单个 Slot，但保留 Worker Agent：

```bat
Worker\stop-slot.bat slot01
```

关闭 Worker 上全部 Slot，但保留 Worker Agent：

```bat
Worker\stop-all-slots.bat
```

推荐按以下顺序停止：

1. 停止全部 Gateway，阻止新播放器连接。
2. 停止全部 Worker Agent。
3. Worker Agent 会停止由它启动的 UE 和 Wilbur。
4. 最后停止 Allocator。

在对应命令窗口按 `Ctrl+C`。Agent 收到退出信号后会清理自己管理的槽位进程。

不要使用 `_stopexe.bat` 停止 Allocator 或 Worker，因为它会按进程名终止当前机器上所有同名 UE 和 Node.js 进程。

## 9. 需要放行的端口

| 来源 | 目标 | 协议和端口 |
|---|---|---|
| 客户端 | Allocator | TCP `9200` |
| Allocator | Worker Agent | TCP `9101` |
| 客户端 | Worker Gateway | TCP `9300` |
| Gateway | 本机 Wilbur | TCP `127.0.0.1:801/802` |
| 客户端 | Worker UE | WebRTC UDP 或 TURN |
| 本机 UE | 本机 Wilbur | `127.0.0.1:8001/8002` |

`8001/8002` 推流端口、远端 `801/802` 和 `9101` Agent API 不应开放给普通客户端。以管理员身份运行：

```powershell
powershell -ExecutionPolicy Bypass -File Gateway\configure-firewall.ps1
```

该脚本放行 Gateway `9300`，并阻止远端直接访问 `801/802`；本机回环访问不受影响。

如果业务页面使用 HTTPS，Gateway 必须配置 `tlsKeyFile`/`tlsCertFile`，并把 `workers.json` 中的 `gatewayUrl` 改成 `https://`。Allocator 会自动生成 WSS 信令地址。

## 10. 当前常见问题

### Allocator 显示 Worker 离线

检查：

```text
Allocator 是否能访问对应 Worker 的 http://WorkerIP:9101/health
Worker 的 authToken 是否与 Allocator 的 token 一致
Windows 防火墙是否允许 9101
```

### 一直停在 starting

检查对应槽位日志：

```text
wilbur.log
ue.log
```

常见原因：

- `windowsDirectory` 或 `gameExecutable` 配置错误。
- Wilbur 端口被占用。
- UE 启动后没有连接到本机 Wilbur。
- WebServers 或 node_modules 文件不完整。
- GPU 显存或视频编码器资源不足。

### 返回 ready，但客户端打不开 Gateway URL

确认：

- `workers.json` 中的 `gatewayUrl` 是客户端实际能够访问的地址。
- 客户端能连接对应机器的 `9300`。
- Gateway 和 Allocator 的 Gateway Token 一致。
- Gateway 返回 `503` 时，检查其能否访问 Allocator `9200`。
- Gateway 返回 `403` 时，Session 可能已释放或 Worker 配置不匹配。

### 浏览器能打开页面但黑屏

重点检查 WebRTC：

- 客户端到 UE 的 UDP 是否可达。
- 跨 NAT 时是否配置并放通了 TURN。
- 浏览器控制台是否显示 ICE 连接失败。

### 同一台机器启动两个 UE

可以共用同一个：

```text
<游戏构建根目录>\Windows\UE_ANDA.exe
```

每个槽位会启动独立的 UE 进程，并使用不同的推流和玩家端口。两个进程仍会分别消耗 GPU、显存和编码资源，并共享 `Saved`、缓存和日志。如果应用会写入用户配置或存档，建议配置独立的用户数据目录。
