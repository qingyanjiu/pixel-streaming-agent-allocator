# Pixel Streaming 认证与密钥说明

本文说明 Worker Token、Allocator API Key、Session Token 的用途、对应关系、错误表现和轮换步骤。

## 1. 一共有几类密钥

当前系统涉及四类认证值，其中前两项是同一个 Worker Token 的两端：

| 密钥 | 配置字段 | 配置位置 | 保护对象 |
|---|---|---|---|
| Worker Token | `authToken` | 每个 Worker 的本机配置 | Worker Agent 管理接口 `9101` |
| Allocator Worker Token | `token` | `Allocator/config/workers.json` | Allocator 访问对应 Worker 时使用的凭据 |
| Client API Key | `apiKey` | `Allocator/allocator.json` | 客户端访问 Allocator 的 Session 和管理接口 |
| Session Token | 创建 Session 时自动返回 | 客户端内存或业务后端 | 查询和释放一个具体 Session |

其中前两项是同一个 Worker Token 的两端：

```text
Worker 本机：
Worker/worker01.json -> authToken

Allocator：
Allocator/config/workers.json -> worker01.token

两者必须完全相同。
```

Client API Key 与 Worker Token 相互独立，不能混用。

## 2. Worker Token 的作用

Worker Token 保护 Worker Agent 的以下接口：

```text
GET  /slots
GET  /slots/{slotId}
POST /slots/{slotId}/start
POST /slots/{slotId}/stop
POST /shutdown
```

Allocator 请求这些接口时会携带：

```http
Authorization: Bearer <worker-token>
```

它能防止未经授权的客户端直接启动或停止 UE 进程。

Worker Agent 的健康检查不需要认证：

```text
GET /health
```

## 3. Worker Token 的配置示例

worker01 的本机配置：

```json
{
  "agentId": "worker01",
  "authToken": "worker01-7f4c9b1d27e8"
}
```

Allocator 的 Worker 配置：

```json
{
  "id": "worker01",
  "baseUrl": "http://192.168.1.21:9101",
  "token": "worker01-7f4c9b1d27e8"
}
```

以下关系必须成立：

```text
worker01.json.authToken == workers.json[worker01].token
```

建议每台 Worker 使用不同 Token。

## 4. Client API Key 的作用

Client API Key 保护 Allocator 的接口：

```text
POST   /api/sessions
GET    /api/sessions/{sessionId}
DELETE /api/sessions/{sessionId}
GET    /api/slots
POST   /shutdown
```

内置流资源驾驶舱也使用同一个 Client API Key。Key 只保存在当前浏览器标签页中。

客户端可以使用：

```http
X-API-Key: <client-api-key>
```

也可以使用：

```http
Authorization: Bearer <client-api-key>
```

配置位于：

```text
Allocator\allocator.json
```

示例：

```json
{
  "apiKey": "client-4d7e89ad123f"
}
```

Allocator 的健康检查不需要认证：

```text
GET /health
```

## 5. 两种 Token 不能混用

错误示例：

```text
客户端使用 Worker Token 调用 Allocator
Allocator 使用 Client API Key 调用 Worker Agent
```

都会返回 `401 Unauthorized`。

正确的调用关系：

```text
Client
  -> X-API-Key: client-api-key
  -> Allocator :9200

Allocator
  -> Authorization: Bearer worker-token
  -> Worker Agent :9101
```

## 5.1 Session Token 的作用

创建 Session 时，Allocator 会自动返回一个随机的 `sessionToken`：

```json
{
  "sessionId": "...",
  "sessionToken": "temporary-session-capability-token",
  "status": "starting"
}
```

查询和释放该 Session 时必须同时携带 Client API Key 和 Session Token：

```http
GET /api/sessions/{sessionId}
X-API-Key: client-api-key
X-Session-Token: temporary-session-capability-token
```

Session Token 用于：

- 区分原 Session 持有者和新申请用户。
- 在断线后的 10 分钟保留期内恢复同一 UE 会话。
- 防止只猜到 Session ID 的其他调用者查询或释放 Session。

Session Token 不是配置项，由 Allocator 每个 Session 自动生成，不能写死在 `allocator.json` 中。

## 6. 不一致时会发生什么

### 本机 Worker Token 与 workers.json 不一致

直接访问 Worker 健康检查仍显示正常：

```text
http://WorkerIP:9101/health
```

因为 `/health` 不需要认证。

但 Allocator 查询 `/slots` 时会收到 `401`，随后把 Worker 标记为离线。

在 `/api/slots` 中可能看到：

```json
{
  "id": "worker07",
  "online": false,
  "lastError": "HTTP 401 from http://192.168.1.27:9101/slots: {\"error\":\"unauthorized\"}"
}
```

### Client API Key 错误

客户端申请 Session 时会收到：

```http
HTTP/1.1 401 Unauthorized
```

### Session Token 错误

返回：

```json
{
  "error": "session_unauthorized"
}
```

前端应清除旧 Session 记录并重新申请，不要使用其他用户的 Session Token。

### Worker 未配置 Token

如果 Worker 的 `authToken` 为空，Agent 会输出警告，并允许所有管理请求访问。正式环境不应这样部署。

### Allocator 未配置 API Key

如果 `apiKey` 为空，客户端管理接口不需要认证。正式环境不应这样部署。

## 7. 生成随机 Token

PowerShell 7 可以运行：

```powershell
$bytes = [Security.Cryptography.RandomNumberGenerator]::GetBytes(32)
[Convert]::ToHexString($bytes).ToLower()
```

Windows PowerShell 5.1 可以使用：

```powershell
$bytes = New-Object byte[] 32
$rng = [Security.Cryptography.RandomNumberGenerator]::Create()
$rng.GetBytes($bytes)
-join ($bytes | ForEach-Object { $_.ToString("x2") })
```

建议至少使用 32 字节随机值，不使用简单密码或机器编号。

## 8. 环境变量配置

Worker 配置可以使用 `authTokenEnv`：

```json
{
  "authTokenEnv": "PS_WORKER_TOKEN"
}
```

Allocator 主配置可以使用 `apiKeyEnv`：

```json
{
  "apiKeyEnv": "PS_ALLOCATOR_API_KEY"
}
```

`workers.json` 中每个 Worker 可以使用 `tokenEnv`：

```json
{
  "id": "worker01",
  "baseUrl": "http://192.168.1.21:9101",
  "tokenEnv": "PS_WORKER01_TOKEN"
}
```

环境变量优先于 JSON 中的明文值。

## 9. 轮换 Worker Token

以 `worker07` 为例：

1. 生成新的随机 Token。
2. 修改该机器上的 `Worker/worker07.json`。
3. 修改 `Allocator/config/workers.json` 中对应 Worker 的 `token`。
4. 重启 `worker07` 的 Worker Agent。
5. 重启 Allocator。
6. 检查 Allocator `/api/slots` 中 `worker07.online=true`。

当 Allocator 与 Worker 短暂不一致时，该 Worker 会暂时离线。

## 10. 轮换 Client API Key

1. 在 `Allocator/allocator.json` 中写入新 `apiKey`。
2. 更新所有受控客户端的 Key。
3. 重启 Allocator。
4. 确认新 Key 可以申请 Session。
5. 确认旧 Key 返回 `401`。

如果由业务后端代理申请，只需要更新后端配置和 Allocator。

## 11. 播放器端口没有 Worker Token

返回给客户端的播放器地址类似：

```text
http://192.168.1.21:801/
```

Wilbur 的玩家接口 `801/802` 当前不使用 Worker Token 或 Client API Key。拥有 URL 的客户端可以连接播放器。

因此：

- Worker Token 只保护 Agent 管理接口。
- Client API Key 只保护 Allocator 管理接口。
- 不要把 Worker Token 放入 `publicUrl`、URL 参数或前端日志。
- 如果播放器也需要用户级权限，需要在 Wilbur 前增加业务鉴权或短期签名 URL；当前实现不提供。

## 12. 安全要求

- 每台 Worker 使用不同的 Worker Token。
- Client API Key 与 Worker Token 分离。
- Session Token 只绑定一个 Session，不能跨 Session 使用。
- 不把 Session Token 输出到公开日志或监控页面。
- 不通过聊天、截图或公开仓库传递正式 Token。
- 不把长期有效的 Client API Key 写入公共网页 JavaScript。
- `Allocator\config\workers.json` 只在 Allocator 和运维网络中分发。
- Worker Agent 的 `9101` 不开放到普通客户端网络。
- 正式环境限制 `corsAllowedOrigins`，不使用 `"*"`。
